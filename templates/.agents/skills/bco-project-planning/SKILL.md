# BCO Project Planning

BCO is authoritative for native task truth. This skill prepares or validates a project plan; it never invents execution authority.

## Workflow

1. Read `ai-docs/bco-project-planning.md`, `ai-docs/bco-automation-readiness.md`, and `references/task-contract.md` completely.
2. Inspect the project brief, repository architecture, commands, tests, existing BCO task truth when exposed, and required environment capabilities.
3. Draft outcome-sized tasks with stable keys. Resolve every dependency to a native key and keep hierarchy separate from execution order.
4. Add enabling tasks for missing contracts, migrations, browser automation, fixtures, infrastructure, or other required capabilities. Mark unresolved capability gaps blocked.
5. Validate unique keys, references, acyclicity, acceptance observability, verification availability, resource ownership, and Git delivery boundaries.
6. Present the dependency graph, rejected ambiguities, capability gaps, and proposed native changes for operator confirmation.
7. Apply only through project-planning mutation capabilities actually exposed by BCO and only when authorized. Otherwise stop at the draft boundary for manual entry.
8. After apply or manual entry, reread authoritative BCO truth and verify native relationships before declaring the plan automation-ready.

Do not create a Markdown backlog as a competing source of truth, connect directly to BCO persistence, turn prose dependencies into assumptions, or use workflow-scoped execution tools to create unrelated project tasks.

## Return

Return the structured task draft or applied change summary, dependency graph, validation outcome, capability matrix, operator decisions still required, and whether BCO truth was reread successfully. Say `draft_only` when no authorized apply capability was available.
