# BCO Project Planning

BCO is authoritative for native task truth. Use semantic judgment to discover and repair deficiencies across the whole plan, including problems not covered by examples. Structural validation supports that reasoning; it cannot decide necessary scope, feasible implementation, or sufficient evidence. This skill prepares or revises a plan and never invents execution authority.

## Workflow

1. Read `ai-docs/bco-project-planning.md`, `ai-docs/bco-automation-readiness.md`, and `references/task-contract.md` completely. For user-visible releases or integration work, also read [Product Acceptance]({{ bcoProductAcceptanceLink }}).
2. Read `ai-docs/context-map.md` when present, the main brief and latest user scope decisions, any supplied plan and audit, and the relevant repository architecture, commands, tests, assets, and exact specialist IDs from `.codex/config.toml`. Inspect existing BCO task truth and runtime capabilities when exposed. Resolve facts through available read-only inspection before asking the user.
3. Choose exactly one mode: create/revise the complete schema-versioned project-plan JSON before import, or produce complete `adopt-existing` JSON from an exact current BCO catalog export. Never mix schemas or use adoption to rewrite task scope. Treat plan JSON, catalogs, and audit reports as temporary operator artifacts, not project authority or deliverables; keep them outside the repository and normally do not commit them.
4. Establish the intended release and explicit exclusions using the scope rules in `ai-docs/bco-project-planning.md`. Distinguish requested outcomes from suggested production methods and example roadmaps. Preserve necessary enabling work without adding unrequested hosting, purchases, human walkthroughs, or physical-device acceptance. If the user explicitly requests external work, retain it and identify its actual provider/authority. Do not quietly delete a requested outcome to claim autonomy.
5. Reason from each outcome back to its inputs, technology, tools, fixtures, resources, and evidence. Choose a feasible implementation within scope, reuse existing foundations, and assign missing producible capabilities to executable predecessor tasks. Record what exists, what a predecessor will supply, and what remains genuinely unresolved. Planning-session tools, package declarations, and model names do not establish workflow capabilities. Empty arrays must not conceal unknown requirements.
6. Draft or repair task definitions and automation contracts together: bounded ownership, `blockedByKeys`, `parentKey`, configured roles, required resources, verification, evidence, and Git delivery. Mentally execute the proposed sequence from the initial checkout through integrated acceptance. Check that setup can start without its own outputs, consumers follow their providers, and repair/candidate capture/review/merge are permitted wherever acceptance needs them.
7. Perform an explicit cross-layer semantic audit against the brief and inspected evidence, challenging your own revised plan. Repair material defects within authorized scope and reassess the affected chain until coherent or a specific unresolved input prevents further progress. Do not repeatedly request unchanged evidence or add work merely to eliminate an uncertainty that does not affect the selected release. Historical failures are reasoning examples, not a closed checklist or keyword-based gate.
8. Validate the exact final JSON through BCO's canonical preview/validate capability when available. Its graph checks include hierarchy as well as dependency edges. Use fresh semantic feedback to revise and re-preview that exact payload; do not conceal a real defect or remove a genuine requirement to pass. If BCO is unavailable, perform the supported local checks and clearly distinguish them from BCO validation. A custom schema/graph check or your own audit is not a passed BCO preview.
9. Return one complete corrected JSON file for paste/upload, not fragments or a patch, plus the concise report below. Keep audit/provenance metadata outside the strict import JSON. In draft-only sessions, leave BCO tasks, project configuration, and EBE unchanged. Apply only after successful canonical preview of that exact payload, through BCO's planning capability within existing user authorization; do not add a second permission request when apply was already authorized.
10. After authorized apply, reread authoritative BCO truth and its automation-readiness report. Distinguish an admitted plan, a launchable initial task, and later tasks waiting for prerequisite outputs. EBE changes launch timing; it cannot resolve unbound scope or missing authority.

Do not create a Markdown backlog as a competing source of truth, connect directly to BCO persistence, turn prose dependencies into assumptions, or use workflow-scoped execution tools to create unrelated project tasks.

## Return

Return the exact schema-versioned JSON file or applied change summary, material corrections and their reasons, selected release and exclusions, prerequisite providers and affected task keys, validation actually performed, and any precise unresolved user decision. Name the first executable work and distinguish future capability waits from defects. Bind validation to the returned file (for example its SHA-256 and preview receipt); changing it invalidates that receipt. Say `draft_only` whenever apply was not performed, even if BCO preview approved it. Never fabricate authority fields for `adopt-existing` or claim successful chaining from plan review alone.
